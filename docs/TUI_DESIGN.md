# TreeSpec Organizer TUI 设计

> 状态：第一期已实现（`organizer tui`）。第 12 节记录了已确认的决定；编辑模式（5.6）暂不实现。

## 1. 目标与边界

TUI 是现有 `organizer` 命令之上的交互前端。它把 README 中“初始化 → 草案 → 审核 → 计划 → 预览 → 执行 → 归档”这条流程放进一个界面，用户不再需要手工拼 `--from/--to/--out` 路径、在 JSON 里找 `run_id`、记住退出码 `2` 的含义，或自己把用完的草案移出 `drafts/`。

文中“基线”指 `.organizer/structure.tree`，即已确认的结构；“草案”指 `drafts/` 下的目标 Tree；“计划”指 `plans/` 下的迁移计划 JSON。

设计约束：

1. **不新增文件操作能力。** 用户文件仍然只由 `apply_plan` 移动。TUI 的每个动作要么对应现有命令，要么对应 README 已要求用户手工完成的步骤（复制基线为草案、编辑草案、归档用完的草案和计划）。归档建议同时补成 CLI 命令，见第 10 节。
2. **安全判断以库为准。** TUI 上的建议和按钮可用性只是提示。真正的检查仍在 `sync`/`chat`/`plan`/`apply` 内部执行，TUI 不缓存“已验证”的结论去替代检查。
3. **按风险分级确认。** 只读动作直接执行；写元数据需要确认；调用模型需要隐私确认；移动文件需要强确认（第 6 节）。
4. **每个动作显示等价命令。** 确认框和命令日志都给出对应的 `organizer ...` 命令行，CLI 始终是行为的参照。
5. **不监听文件系统。** 只在启动、手动刷新和每次写操作后扫描，与规范“无后台监听”一致。

不在范围内：删除文件或目录、撤销迁移、续跑中断的迁移、跨卷移动、多轮对话、GUI 和以鼠标为主的交互。这些在 CLI 中同样不支持，TUI 不绕开。

## 2. 启动与整体结构

入口为 `organizer tui [--root PATH]`。根目录解析与其他命令相同：显式 `--root`，否则从当前目录向上找最近的 `.organizer`。根目录在会话内固定，切换需要退出重进；找不到时进入初始化页。

```text
TreeSpec Organizer  /Users/me/Workspace  LLM gpt-x@api.example.com  扫描 10:42
[1 概览]  2 结构  3 整理  4 历史  5 恢复
────────────────────────────────────────────────────────────────────────────────

                               当前页面内容

────────────────────────────────────────────────────────────────────────────────
下一步：由状态模型计算的一句建议
当前页面的快捷键提示                                    ? 帮助   L 日志   q 退出
```

顶栏显示根目录、LLM 配置摘要和最近一次扫描时间。LLM 摘要在启动时读取环境变量，用与 `chat` 相同的配置与端点策略校验（不联网），显示“模型@主机（本地/远程）”、“未配置”或“已禁用”，从不显示 API Key。底栏第一行是由第 3 节状态模型算出的下一步建议，每个页面都显示；第二行是当前页面的快捷键。

| 页面 | 用途 | 对应命令 |
| --- | --- | --- |
| 1 概览 | 工作区状态、磁盘变化、进行中的整理轮次、同步 | `status`、`sync` |
| 2 结构 | 浏览基线，选择 LLM 范围 | 读取 `structure.tree` |
| 3 整理 | 草案、审核、计划与预览、执行、归档 | `chat`、`validate`、`plan`、`apply`、`export-script`、归档 |
| 4 历史 | 结构提交与迁移运行记录 | `history` |
| 5 恢复 | 检查未完成的迁移，补记 Git | `recover` |

恢复页平时置灰。检测到未完成迁移时，TUI 启动后直接进入恢复页，其他页面的写操作全部禁用，直到恢复检查显示 `complete`。

## 3. 状态模型

### 3.1 工作区状态

启动、刷新和每次写操作后，TUI 把工作区归入下表一种状态，从上到下判断，命中即停。前三种状态下 `status` 本身会报错，所以 TUI 先做只读探测（检查标记文件、读取操作日志），再决定是否调用 `status`。

| # | 状态 | 判断依据 | 可用动作 |
| --- | --- | --- | --- |
| 1 | 未初始化 | 找不到 `.organizer` | 初始化 |
| 2 | 元数据中断 | `state/` 下的 `index.sqlite` 或 `operations.sqlite` 有 `-journal`/`-wal`/`-shm` 恢复文件；或存在 `pending.json` 但没有未完成运行 | 只读查看标记内容和 `sync.log`，提示先备份 `.organizer` 再人工检查 |
| 3 | 迁移未完成 | 操作日志中存在状态不是 `complete` 的运行 | 进入恢复页 |
| 4 | 基线冲突 | `structure.tree` 与索引记录的基线不一致，或 Git 检查失败 | 只读查看冲突原文；可把当前 `structure.tree` 另存为新草案，作为人工恢复的第一步 |
| 5 | 扫描不完整 | `scan_complete = false` | 查看出错路径，修正权限后按 `R` 重新扫描 |
| 6 | Git 待补记 | `pending_git = true` | 同步（重试 Git 记录） |
| 7 | 磁盘有变化 | added/missing/moved/changed/unknown 任一非空 | 同步；有进行中的轮次时先归档 |
| 8 | 已同步 | 以上都不是 | 全部整理动作 |

根目录路径或身份变化、元数据锁被其他进程占用等情况会直接以错误返回，不在上表中。TUI 显示错误原文，保持只读，允许按 `R` 重试。

状态 4 到 8 都可以浏览和归档整理轮次，因为归档只在 `.organizer` 内部移动草案和计划，不触及基线。有两条特殊规则：

**磁盘有变化时禁止新建草案（包括手工草案）。** `sync` 遇到 `drafts/` 或 `plans/` 中有文件会停止，`chat`/`plan`/`apply` 遇到过期基线也会停止。如果允许先建草案，用户会两头受阻。TUI 因此固定顺序：归档旧轮次 → 同步 → 新建草案。新建草案只在状态 8 可用；状态 4 的“另存为新草案”是唯一例外。“仅内容变化”（changed）不产生结构提交，但 `plan`/`apply` 仍要求同步，所以同样计入。

**待处理草案不算冲突。** `status` 的 `conflicts` 字段把“`drafts/`、`plans/` 中有待处理文件”和真正的基线冲突合在一起，CLI 因此返回 `2`。TUI 把前者单独显示为“进行中的整理轮次”，只有后者进入状态 4。

### 3.2 整理轮次

一轮整理以一个草案文件为中心，包括它的审核报告 `NAME.tree.review.json`（仅 LLM 草案有）和由它生成的计划。计划与草案按内容配对，不按文件名：把草案用当前基线规范化后求摘要，与计划的 `target_tree_digest` 比较。草案在计划生成后又被编辑，旧计划就失去配对，归入“未关联计划”分组，只能查看和归档，不能从 TUI 执行；要执行需对当前草案重新生成计划。找不到草案的审核报告标为“孤立报告”，建议归档。

每轮的阶段按下表从上到下判断（`base`、`target` 指计划记录的基线与目标摘要，“当前”指当前基线摘要）：

| 阶段 | 判断依据 | 下一步 |
| --- | --- | --- |
| 草案无效 | 解析失败，或审核标记/报告缺失、重复，或报告的根目录不符 | 显示错误行号，打开编辑器修正 |
| 草案过期 | LLM 报告的 `base_tree_digest` ≠ 当前 | 归档，重新生成 |
| 待计划 | 草案有效，没有配对计划 | 生成计划 |
| 计划不可执行 | 配对计划的 `unresolved` 非空（TUI 不保存这类计划，只可能来自 CLI，见 4.5） | 回到草案修改 |
| 计划已过期 | `base` ≠ 当前，且 `target` ≠ 当前 | 重新生成计划 |
| 可执行 | `base` = 当前，`target` ≠ 当前 | 预览、执行 |
| 无需执行 | `base` = `target` = 当前 | 归档 |
| 已执行 | `target` = 当前，`base` ≠ 当前 | 归档（可用操作日志中该 `plan_id` 的 `complete` 记录佐证） |

阶段之外还有一个独立标记“需确认审核”：LLM 报告的 `unresolved` 非空，或草案规范化后的摘要 ≠ 报告的 `target_tree_digest`（生成后被编辑过）。带此标记的草案生成计划前必须先确认审核，对应 `plan --acknowledge-review`。

手工草案没有报告，过期只能在生成计划时以“缺失文件”“无来源新文件”等未解决项体现，计划视图会直接列出。“可执行”只反映生成计划那一刻；磁盘之后仍可能变化，所以预览结果始终带“执行前会重新检查”的提示，预览通过的标记只存在于本次会话内存，不写盘。工作区不处于状态 8 时，所有轮次的计划、预览、执行动作置灰，阶段旁标注受阻原因（例如“受阻：磁盘有变化”）。

## 4. 主要流程

### 4.1 首次使用

在未初始化目录启动时进入初始化页，显示将要管理的绝对路径，并说明初始化会扫描目录、创建 `.organizer/`（结构文本、SQLite 索引、只记录结构的 Git 仓库），不移动任何文件。路径是 `$HOME`、`/` 或其他明显过大的目录时额外提示扫描可能很慢。按 `i` 弹出确认框，确认后执行 `init`，完成后进入概览页。

### 4.2 记录在 TUI 之外完成的调整

用户在文件管理器里移动了文件后，概览页列出新增、缺失、移动、仅内容变化和未知身份。按 `s` 弹出同步确认框，按类别汇总将要记录的变化，并说明“缺失只从结构快照移除，不删除磁盘文件，也无法恢复其内容”。

存在未知身份时，确认框逐项列出路径、候选 ID 和原因，并附一个默认不勾选的选项“将这些记录为旧节点消失 + 新节点出现”。不勾选不能确认，勾选后对应 `sync --accept-unknown`。有进行中的整理轮次时 `s` 置灰，底栏提示先到整理页归档。

### 4.3 用 LLM 生成草案

在整理页按 `n`，或在结构页选好范围后按 `c`，打开“新建 LLM 草案”对话框，包含请求文本（单行，最多 8192 字节，实时显示字节数）、范围、两个开关（允许重新分类 `--classify`，发送文本片段 `--read-content`）和输出文件名（默认 `chat_XXXXXXXX.tree`，8 位随机十六进制，可改为 `drafts/` 下的其他新名称；CLI 允许写到根目录之外，TUI 只用 `drafts/`，以便识别整理轮次）。对话框同时显示将发送到哪里、发送什么，见 5.4。`ORGANIZER_LLM_NO_CONTENT=1` 时“发送文本片段”置灰；LLM 未配置或已禁用时 `n` 只提供手工草案，并说明原因。

确认后在后台调用模型，显示等待状态和已用时间。等待不可取消：HTTP 调用是同步的，单次超时 30 秒，一次 `chat` 最多两次 TreeEditor 和两次 FileMapper 调用。强制退出不会留下缺少报告的草案，因为库总是先写报告再写草案，最坏情况只留下孤立报告。完成后跳到该轮的审核视图；有待审核项时（CLI 退出码 `2`）焦点直接落在第一个待审核项上。

### 4.4 手工草案

按 `n` 选择“复制当前结构”，输入文件名（默认 `new.tree`，已存在则建议 `new-2.tree`），TUI 在 `drafts/` 下只新建、不覆盖，等价于 README 中的 `cp -n`。之后按 `e` 用外部编辑器打开。

外部编辑器依次取 `$VISUAL`、`$EDITOR`，都没有时用 `vi`。TUI 先恢复终端，把编辑器设置按空白拆成程序和参数，草案路径作为单独参数追加，不经过 shell 插值。编辑器退出后重新解析草案并刷新该轮阶段；解析失败时显示行号，再按 `e` 重新打开。编辑 LLM 草案前提示一次：保留首行 `# organizer-review-v1: …` 标记；编辑后生成计划需要确认审核。

### 4.5 审核、计划、预览与执行

在审核视图检查目标结构和报告后按 `p`。草案带“需确认审核”标记时，先弹出确认框说明原因（有待审核项，或生成后被编辑），要求勾选“我已检查完整草案和报告；未分类文件保持原有归属”，并写明这一步不绕过路径、身份、源文件和冲突检查。

后台执行与 `plan` 相同的逻辑。结果有 `unresolved` 时不写计划文件，只在计划视图列出未解决项，建议回到草案修改。否则写入新文件（写入前可修改文件名）：普通草案默认为 `plans/NAME.json`，确认审核后为 `plans/NAME.reviewed.json`，重名追加 `-2`、`-3`。

按 `d` 预览，等价于 `apply --dry-run`，只读，不需要确认。按 `A` 执行：TUI 先自动预览一次，通过后弹出强确认框（5.3），要求输入 `apply`；确认后在后台执行，显示“第 k / n 步”。成功后显示 `run_id`、完成的操作数和新的 Git 提交，该轮变为“已执行”。阶段为“无需执行”时 `A` 置灰；只改说明、没有文件操作的计划仍会更新结构记录，不属于“无需执行”。

### 4.6 归档

`z` 归档当前轮次：草案、审核报告、配对的计划及其导出脚本一起移到 `.organizer/archive/<时间戳>-<草案名>/`。`Z` 归档 `drafts/` 和 `plans/` 下的全部内容，包括孤立报告和未关联计划。归档使用不覆盖的移动，确认框列出每个将被移动的文件。放弃草案同样通过归档完成，TUI 不提供删除。归档后这些文件不再阻止 `sync`，又因为位于 `.organizer` 内部，不会被扫描成用户文件。

### 4.7 执行失败

预检阶段被拒绝时（计划过期、磁盘变化等）还没有创建运行，错误框只显示原始错误，工作区状态不变。执行开始后失败时，错误中带 `run_id`，按 Enter 进入恢复页；此时工作区处于状态 3，其他页面的写操作全部禁用。

### 5.2 结构

基线的只读浏览器，目录可折叠。`[X]` 表示敏感名称（如 `.env`、私钥）或受保护的嵌套 Git 项目，不能作为 LLM 候选，也不能选为范围。Space 多选目录作为范围（`[*]`），对应可重复的 `--scope`；按 `c` 以所选范围打开 5.4 的对话框。`/` 按名称搜索，`i` 显示完整 ID。

### 5.3 整理

左栏是整理轮次列表，右栏顶部是步骤条“草案 → 审核 → 计划 → 执行 → 归档”，下面是当前轮次的视图。预览并入“计划”一步。

**审核视图**展示带标注的目标树：`+` 新目录，`~` 改名，`>` 移到新的父目录，`^` 仅随祖先改变路径，`#` 说明变化，`?` 待审核，`!` 阻断项。标注来自 `compare_trees` 的 `changes` 与 `effective_path_changes`，以及审核报告的 `assignments`、`unresolved`。目标中缺失的旧节点不在树里，单独列在树下方，标 `!`。`f` 只显示有变化的节点（保留祖先以便定位）。选中节点时下方显示旧路径、新路径，以及 LLM 的决定（`place`/`keep`/`review`）和理由。`v` 在审核、计划、报告三个视图间切换（跳过不可用的）；报告视图显示编辑数、读取的正文字节数、全部分配和警告。

### 5.5 历史与恢复

历史页左栏是结构提交（`history` 的短哈希和提交说明，按 `init`/`reconcile`/`refactor` 标注类型），右栏是迁移运行记录（`run_id`、`plan_id`、状态、完成步数），需要第 10 节第 2 项。第三期可按提交查看当时的结构并与当前基线比较。

恢复页显示未完成运行的检查结果。“当前磁盘”一列由 TUI 用 `recover` 返回的当前扫描与计划前置条件按路径和文件键比对得出，只是供人工核对的提示，不代表身份确认，也不会触发任何操作。

```text
──────────────────────────────────────────────────────────────────────────────
run_7b2e…   状态 failed   已确认 3/5   plan sha256:41a9…
错误：migration run_7b2e… stopped after 3/5 acknowledged operations: …

步骤  状态     操作                                         当前磁盘
  1   done     move_directory  Inbox → Incoming             在目标
  2   done     mkdir           Research/Papers/C2Rust       在目标
  3   done     mkdir           Research/Papers/Security     在目标
  4   pending  move_file       …/CRUSH.pdf → …/C2Rust/      在源
  5   pending  move_file       …/ASLR.pdf → …/Security/     在源

只读检查。pending 可能已落盘但未确认，不要重新执行计划。
部分完成的文件步骤需人工核对；TUI 不提供续跑或回滚。
──────────────────────────────────────────────────────────────────────────────
Enter 步骤详情   R 重新检查   F 补记 Git（本状态不可用）   ? 帮助
```

| 运行状态 | 含义 | `F` 补记 Git |
| --- | --- | --- |
| `pending`/`failed` | 文件步骤可能部分完成，需人工核对 | 仅当全部步骤已确认、且无发布标记时可尝试 |
| `publishing`，有发布标记 | 结构或索引发布中断 | 不可用；提示先备份 `.organizer` 再人工检查 |
| `publishing`，无发布标记 | 移动已完成，元数据可能已发布 | 可尝试，由库核对元数据 |
| `git_pending` | 移动和元数据都已完成，只差 Git 记录 | 可用 |

`F` 等价于 `recover RUN_ID --finish-git`，使用普通确认。是否真正允许由库判断，TUI 的置灰只是提示。

`M` 等价于新增的 `recover RUN_ID --mark-resolved`（第 12 节决定 5）：用户人工核对磁盘后，关闭一个从未开始发布元数据的 `pending`/`failed`/`publishing` 运行。它不移动文件，不修改基线、索引或 Git；计划 ID 在操作日志中唯一，所以该计划永远不能再执行。确认框要求勾选“我已人工核对每个步骤的源和目标”。之后先归档这一轮，再同步，记录磁盘的实际状态。存在发布标记或 `git_pending` 时库会拒绝，分别提示人工检查或改用 `F`。

### 5.6 编辑模式（暂不实现，见第 12 节决定 4）

在审核视图按 `E` 进入，直接修改内存中的草案 AST。每一步立即校验，不合法的操作被拒绝并说明原因。

| 键 | 操作 | 限制 |
| --- | --- | --- |
| `a` | 在光标所在目录（文件则取其父目录，顶部根行即管理根）下新建目录，输入名称和可选说明 | 名称须是合法的单个路径段，同级不重名；新目录分配随机 `d_` ID |
| `r` | 改名（文件或目录） | 同上 |
| `c` | 设置或清除说明 | 单行，不含控制字符 |
| Space | 标记或取消标记节点 | 可多选 |
| `m` | 把已标记节点移入光标所在目录 | 不能移入自身后代，不能造成重名；含扫描边界的目录不能移动，节点也不能移入边界内 |
| `u` | 撤销上一步 | 内存中的快照栈 |
| `w` | 保存 | 写回文件，重新计算阶段 |
| Esc | 退出编辑模式 | 有未保存修改时询问 |

刻意不提供删除节点、新增文件、修改 ID 和移除空目录声明。前两项会产生“缺失文件”或“无来源新文件”，修改 ID 会破坏身份对应，移除目录声明在 M2 中只会变成未解决项。

保存时把草案规范化写回原文件，LLM 草案保留首行审核标记。这是 TUI 唯一一处原地改写：LLM 报告按文件名与草案配对，另存新文件会断开配对。为不覆盖外部修改，保存前比较文件当前内容与载入时的摘要，不一致则拒绝保存并提示重新载入。规范化会丢弃手写的空行和独立注释，进入编辑模式时提示一次。

## 6. 确认与安全规则

| 风险 | 动作 | 交互 |
| --- | --- | --- |
| 只读 | 扫描、浏览、`validate`、Diff、预览、历史、恢复检查 | 直接执行 |
| 只新建文件 | `plan`、复制基线为草案、导出脚本 | 只需确认文件名 |
| 写 `.organizer` 内部 | `init`、`sync`、归档、`recover --finish-git` | 普通确认：列出将写入或移动的内容和等价命令，按 `y` 确认 |
| 关闭失败运行 | `recover --mark-resolved` | 普通确认，并要求勾选“已人工核对” |
| 向外部服务发送数据 | `chat` | 隐私确认：显示目标主机、本地或远程、发送内容和排除数量 |
| 移动用户文件 | `apply --yes` | 强确认：先自动预览，再要求输入 `apply` |

其他规则：

- 普通、隐私和强确认框的默认焦点都在“取消”，连续按 Enter 不会确认这些写操作。
- 执行期间 `q` 无效。第一次 Ctrl-C 只提示“中止会留下部分完成的迁移，需要人工恢复”，3 秒内再按一次才退出。TUI 不提供在步骤之间“安全停下”，因为部分完成的迁移无法续跑，通常比等它完成更糟。终端被关闭或进程被杀时依靠操作日志，下次启动进入恢复页。
- 文件名、说明、LLM 理由和错误原文都视为不可信数据，渲染前转义控制字符（显示为 `\u{…}`），防止终端转义序列注入。
- TUI 不提供任何跳过检查的选项。库拒绝时显示原始错误，没有“仍然继续”。

## 9. 实现方案

### 9.1 调用方式

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 进程内调用 `organizer` 库 | 直接得到 `ReconcileReport`、`MigrationPlan`、`ChatReport`、`RecoveryReport` 等类型；可加执行进度回调；不解析文本 | 需要补少量公开接口（第 10 节） |
| 子进程调用 CLI，解析 JSON | 行为与命令行逐字一致，不改库 | 错误只能匹配英文 stderr；没有执行进度；状态判断依赖退出码和字符串，容易出错 |

选择进程内调用。TUI 作为 `organizer tui` 子命令放在二进制一侧（与 `main.rs` 同属 bin target），只能使用库的公开接口，因此不会绕开 CLI 走的路径；第 10 节的缺口都以公开接口补齐。为保持与 CLI 一致，每个动作的库调用参数和等价命令行由同一份参数结构生成，单元测试用 `Cli::try_parse_from` 解析生成的命令行，检查得到的命令与动作参数相同。`ratatui` 和 `crossterm` 放在默认开启的 `tui` feature 下，只用 CLI 的用户可以关掉。

### 9.2 线程与锁

UI 线程只负责渲染和按键。扫描、`chat`、`plan`、预览、执行和恢复检查都放到一个工作线程串行执行，通过 channel 回传结果；同一时间只运行一个任务，运行时写操作置灰，只读浏览仍可用。

TUI 空闲时不持有元数据锁，每次库调用像 CLI 一样自行获取和释放。另一个 `organizer` 进程占用锁时显示“元数据正被其他进程使用”，保留上次数据并标为可能过期。因为界面状态随时可能过期，每个写动作都由库重新检查，不依赖界面上的判断。

### 9.3 模块

```text
src/tui/                 # 属于二进制，只用库的公开接口
├── mod.rs               # 入口；终端初始化与恢复；事件循环；外部编辑器
├── action.rs            # 动作 → 等价命令行（argv、显示用 shell 转义）
├── worker.rs            # 后台线程：串行执行动作和刷新，回传事件
├── load.rs              # 刷新时的全部读盘：probe、status_detailed、草案/计划、check_review
├── state.rs             # 纯函数：工作区状态（第 3.1 节）
├── rounds.rs            # 纯函数：草案、报告、计划配对与阶段（第 3.2 节）
├── review.rs            # 审核视图的标注
├── tree_index.rs        # 预计算的子节点顺序、路径和折叠状态
├── text.rs              # 控制字符转义、CJK 宽度、截断、中文错误建议
├── llm_info.rs          # 离线校验 LLM 配置，生成顶栏摘要
├── app/                 # 应用状态；按键只排队任务，不做 I/O
│   ├── events.rs        # 处理快照和动作结果
│   ├── keys*.rs         # 全局与各页面按键
│   └── dialog.rs        # 确认框、强确认、chat 表单、输入框
├── view/                # 渲染：概览、结构、整理（审核/计划/报告）、历史、恢复、对话框
└── tests/               # argv 与 CLI 解析一致性；在真实临时目录上驱动 App 的流程测试
```

`state.rs`、`rounds.rs` 和 `review.rs` 不做 I/O，便于单元测试。

### 9.4 显示

用 `unicode-width` 计算中英文混排宽度，长路径在中间省略（如 `Research/…/CRUSH.pdf`）。颜色只作辅助，每种状态都有文字或符号标记，并遵守 `NO_COLOR`。大树只渲染可见行。终端窄于 80 列时两栏改为单栏，用 Tab 切换。

### 9.5 测试

`state.rs`、`rounds.rs` 用单元测试覆盖第 3 节的每种工作区状态和轮次阶段，包括由构造的探测结果判断进入恢复页。关键页面用 ratatui 的 `TestBackend` 渲染并检查显示内容（转义、标注、窄终端单栏）。动作层在临时目录上调用库，配合 Mock LLM（`chat_with_provider` 接受任意 `LlmProvider`），覆盖“初始化 → 同步 → 草案 → 计划 → 预览 → 执行 → 归档”的闭环。

## 10. 底层接口（第 1–7 项已实现）

TUI 只使用库的公开接口（9.1）。现有的 `sync::{init, status, sync, history, resolve_root}`、`migration::{plan, validate_plan, apply_plan, export_script, journal::recover}`、`llm::{chat_with_provider, check_review, review_path}`、`tree::{parse_tree_with_base, render_tree, compare_trees}` 已覆盖大部分功能。第一期补充的接口如下，括号内为实际名称：

1. **待处理文件与冲突分开**（`sync::status_detailed`，返回 `pending` 和 `baseline_conflicts`）。`status` 的 CLI 输出保持不变。
2. **列出运行**（`migration::journal::list_runs`、`RunSummary`）。新增终态 `resolved`，与 `complete` 一样不阻塞后续命令。
3. **元数据中断探测**（`workspace::probe`）。持有共享锁读取，正在进行的更新报告为“忙”，不会误判为中断。
4. **带进度回调的执行**（`migration::apply_plan_with_progress`）。回调只用于显示，不能中止执行。
5. **归档命令**（`organizer archive [ENTRY...] [--all]`、`workspace::archive`）。LLM 草案与其审核报告总是一起移动。
6. **草案文件写入**（`workspace::copy_baseline_draft`、`workspace::check_new_name`）。编辑模式暂不实现，所以只提供“只新建”。
7. **LLM 范围预览**（`llm::preview_scope`、`llm::excluded_ids`）。不扫描、不联网，与 `chat` 使用同一范围校验。

另外为第 12 节决定 5 新增 `migration::journal::mark_resolved`（`organizer recover RUN_ID --mark-resolved`），并把 `plan` 的完整逻辑提取为 CLI 与 TUI 共用的函数，保证两者执行相同的审核检查。仍待实现：

## 12. 已确认的决定

1. 入口为 `organizer tui` 子命令，放在默认开启的 `tui` feature 下；`cargo install --no-default-features` 得到不含 TUI 依赖的纯 CLI。

6. 界面用中文；库的英文错误原样显示，常见错误另附一行中文建议（按错误文本中的固定短语匹配，未匹配时只显示原文）。
